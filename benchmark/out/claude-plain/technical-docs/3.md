# Rebase vs. Merge: When to Use Which

Both commands integrate changes from one branch into another, but they do it differently, and that difference is what causes confusion.

**Merge** creates a new commit that ties together two histories. Nothing is rewritten — every commit keeps its original hash, and you get an accurate (if messy) record of when branches diverged and reconverged.

**Rebase** replays your commits on top of another branch, one by one, producing new commits with new hashes. The result looks like you branched off the latest code and worked in a straight line — history is cleaner, but the original commits are gone.

## The rule of thumb

**Never rebase a branch that others are pulling from or building on.** Rebasing rewrites history; anyone with a copy of the old commits will get conflicts or duplicate commits when they pull. This is why you should never rebase `main` or any shared long-lived branch.

**Feel free to rebase your own feature branch before it's shared**, or one only you are pushing to. This keeps history clean and makes review easier.

## Practical guidance

- **Updating your feature branch with the latest `main`:** prefer `git rebase main` while you're still the only one working on the branch. It avoids a pointless "merge main into feature" commit and keeps your commits readable.
- **Once you've opened a PR and others may have pulled your branch (or added review commits):** switch to merging `main` in, or just keep pushing and let the reviewer deal with a few merge commits. Don't force-push a rebase over commits someone else is looking at without a heads-up.
- **Merging your finished feature branch into `main`:** use a regular merge (or your platform's "squash and merge" / "rebase and merge" PR button, which handles this safely for you). Never rebase `main` itself onto your feature branch.
- **If you must rebase a branch that's already pushed:** communicate first, and use `git push --force-with-lease` (not `--force`) so you don't clobber commits you haven't seen.

## Quick mental model

- Merge = "combine histories, keep the truth of what happened."
- Rebase = "pretend I started from the latest code" — clean, but rewrites truth.

If you're not sure which to use, ask: **has anyone else seen these commits?** If no, rebase is safe and often nicer. If yes, merge (or communicate loudly before rebasing).
