Consistent hashing is a technique for mapping keys to nodes (e.g., cache servers) in a way that minimizes remapping when the set of nodes changes. It's the standard approach for distributing keys across a cache cluster, and it solves a specific failure mode of naive modulo hashing.

**Simple modulo hashing:** With `N` cache servers, a key is assigned to `hash(key) % N`. This is simple and gives an even distribution, but it's brittle: if `N` changes — a node is added, removed, or crashes — the modulus changes, and `hash(key) % N` produces a different result for nearly every key. In practice, adding or removing even one server invalidates roughly `(N-1)/N` of all cached entries. For a large cluster, that's close to 100% of your cache being invalidated at once, causing a "thundering herd" of cache misses hitting the backend simultaneously.

**Consistent hashing:** Instead of hashing keys directly onto a node count, both keys and nodes are hashed onto the same fixed circular space (a "hash ring," typically 0 to 2^32-1). Each node occupies one or more points on the ring (often many "virtual nodes" per physical node, to smooth out distribution). To find which node owns a key, you hash the key and walk clockwise around the ring until you hit the first node.

When a node is added or removed, it only affects the portion of the ring between it and its immediate neighbor. Keys elsewhere on the ring are unaffected. This means only about `K/N` keys need to move (where `K` is the total key count and `N` is the number of nodes) — proportional to the size of the change, not the size of the whole cluster.

**Why this matters for caches specifically:**
- **Scaling elasticity:** Cache clusters often grow/shrink to match load. Consistent hashing lets you do this without a mass cache-invalidation event.
- **Failure tolerance:** A crashed node only disrupts its own slice of keys; the rest of the cluster keeps serving hits normally.
- **Reduced backend load spikes:** Because remapping is localized, you avoid the correlated flood of cache misses (and resulting database/backend load) that modulo hashing causes on every topology change.

**Practical refinements:**
- **Virtual nodes:** Mapping each physical server to many points on the ring avoids uneven load when node counts are small or hashes cluster unevenly.
- **Bounded load variants** (e.g., "consistent hashing with bounded loads") cap how much any one node can be overloaded relative to average.
- **Alternatives:** Rendezvous hashing (highest random weight) achieves similar remapping-minimization properties without an explicit ring, and is used in some systems (e.g., some CDNs) as a simpler alternative.

In short: modulo hashing ties key placement to the exact node count, so any topology change reshuffles almost everything; consistent hashing decouples them, so changes only disturb the keys near the change — which is essential for caches that need to scale and tolerate failures without collapsing hit rates.
