# Runbook: Pod Stuck in CrashLoopBackOff

## 1. Confirm the symptom

```
kubectl get pods -n <namespace>
```

Look for `CrashLoopBackOff` status and check `RESTARTS` count to gauge severity.

## 2. Gather evidence

```
kubectl describe pod <pod> -n <namespace>
kubectl logs <pod> -n <namespace> --previous
kubectl logs <pod> -n <namespace> -c <container>   # if multi-container
```

- `describe` shows recent Events (OOMKilled, failed liveness probe, image pull errors, scheduling issues).
- `--previous` gets logs from the crashed instance, not the current restarting one.

## 3. Identify the failure category

**Application error** — logs show a stack trace, unhandled exception, or fatal startup error immediately after boot.

- Check recent deploys/config changes (`kubectl rollout history`).
- Reproduce locally or in a scratch pod with the same image/env.

**OOMKilled** — `describe` shows `Reason: OOMKilled`.

- Check memory usage trend (`kubectl top pod`), raise `resources.limits.memory`, or fix a leak.

**Failed liveness/readiness probe** — Events show probe failures triggering restarts.

- Verify probe path/port is correct and the app is actually ready within `initialDelaySeconds`.
- Temporarily loosen probe timing to see if the app just needs more startup time.

**CrashLoop from bad config/secrets** — app exits immediately (exit code 1) due to missing env var, bad config file, or failed dependency connection (DB, cache).

- Check `kubectl exec` into a debug pod with the same image to inspect mounted config/secrets.
- Verify `ConfigMap`/`Secret` references and that dependent services are reachable (DNS, network policy).

**ImagePullBackOff masquerading as crash loop** — check `describe` for pull errors; not a true crash but often confused with one.

**Command/entrypoint issue** — container exits instantly (RESTARTS climbing fast, low uptime each cycle).

- Check `kubectl get pod <pod> -o yaml` for `command`/`args` overrides; test the entrypoint manually via `kubectl run --rm -it --image=<image> -- sh`.

## 4. Check exit code

```
kubectl get pod <pod> -n <namespace> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}'
```

- `0`: clean exit but process ended (often a misconfigured foreground command).
- `1`: generic app error — check logs.
- `137`: SIGKILL — usually OOMKilled or manual kill.
- `143`: SIGTERM — graceful shutdown, check if probes/preStop hooks are too aggressive.

## 5. Fix and validate

- Apply the fix (image, config, resources, probe settings) via your normal deploy path (`kubectl apply`, Helm, GitOps PR).
- Watch the rollout:

```
kubectl rollout status deployment/<name> -n <namespace>
kubectl get pods -n <namespace> -w
```

- Confirm `RESTARTS` stabilizes and status reaches `Running`/`Ready`.

## 6. Post-incident

- Add/adjust alerting on restart count if this wasn't caught early.
- If OOM or probe-related, consider adding resource requests/limits tests to CI to catch regressions before deploy.
