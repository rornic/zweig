The CAP theorem states that a distributed data store can provide at most two of three guarantees simultaneously:

- **Consistency (C)**: every read receives the most recent write or an error — all nodes see the same data at the same time.
- **Availability (A)**: every request to a non-failed node receives a response, without guarantee it's the latest write.
- **Partition tolerance (P)**: the system continues operating despite arbitrary message loss or delay between nodes (a network partition).

The key insight is that this isn't really a free three-way choice. In any distributed system, network partitions *will* happen — cables get cut, switches fail, packets drop. Since partition tolerance isn't optional for a system spread across multiple nodes, the real choice CAP forces is between **C and A specifically during a partition**. When nodes can't communicate:

- Choose **CP**: nodes on the minority side of the partition refuse writes (or reads) to avoid serving stale or divergent data. The system sacrifices availability to guarantee consistency. Example: a system that returns an error rather than risk serving outdated data — e.g., HBase, or Zookeeper for its coordination data.
- Choose **AP**: every node keeps accepting reads and writes even though they can't sync with each other, so different clients may see different values until the partition heals. The system sacrifices consistency to stay available. Example: Cassandra or DynamoDB in their default configurations.

When there's *no* partition, a system can actually be both consistent and available — CAP only bites during the partition window. This is why the more useful mental model (from Daniel Abadi's PACELC extension) is: **if Partitioned, choose A or C; Else, choose Latency or Consistency.** Even without a partition, systems trade consistency against latency, which CAP alone doesn't capture.

A few common misreadings worth avoiding:
- CAP doesn't mean "pick any two" as a static architectural label (you can't just discard partition tolerance for a genuinely distributed system).
- Consistency here means linearizability, not the "C" in ACID.
- Real systems often blend the choice per-operation or let it be tunable (e.g., Cassandra's per-query consistency levels, DynamoDB's eventually-vs-strongly-consistent reads) rather than being purely CP or AP everywhere.

In practice, the theorem is a lens for reasoning about failure-mode tradeoffs, not a rigid classification — the interesting engineering happens in *how* a system degrades gracefully during the partition and reconciles state afterward (e.g., conflict resolution, read repair, vector clocks).
