## Autovacuum

Postgres uses MVCC: an `UPDATE` doesn't overwrite a row in place, it writes a new row version and marks the old one as dead (a `DELETE` just marks it dead). Dead tuples can't be removed immediately because other transactions might still need to see them. Autovacuum is a background process that periodically scans tables, reclaims space from dead tuples so it can be reused by future writes, updates the visibility map (so index-only scans can skip heap lookups), and updates planner statistics. It also handles transaction ID (XID) wraparound by freezing old tuples before the 32-bit XID counter cycles.

Autovacuum runs automatically when a table's estimated dead-tuple count crosses a threshold (`autovacuum_vacuum_threshold` + `autovacuum_vacuum_scale_factor` × row count, defaults 50 + 20%). A separate `ANALYZE` threshold triggers stats updates.

## Why bloat happens without it

Every `UPDATE`/`DELETE` leaves a dead tuple behind. If autovacuum doesn't run often enough (disabled, tuned too conservatively, or falling behind on a high-churn table), dead tuples accumulate faster than they're reclaimed. Postgres can't shrink the file on disk by just removing them — regular `VACUUM` only marks the space free-list-available for reuse *within* the table file, it doesn't return space to the OS. So the table (and its indexes) grow larger than the live data requires — "bloat." Symptoms: slower sequential scans and index scans (more pages to read for the same data), worse cache hit rates, and increased disk usage. Long-running transactions or idle-in-transaction sessions make it worse because they hold back the oldest visible snapshot, preventing dead tuples from being cleaned up at all.

## Telling if a table needs a manual VACUUM

- **Dead tuple ratio**: query `pg_stat_user_tables` — `n_dead_tup` vs `n_live_tup`. A dead ratio much above the autovacuum threshold (roughly >20% and growing) suggests autovacuum isn't keeping up.
- **Last vacuum time**: check `last_vacuum` / `last_autovacuum` in the same view — if it's stale relative to write volume, something's blocking or throttling it.
- **Bloat estimate**: use an extension like `pgstattuple` (`pgstattuple('table')` gives actual dead tuple % and free space) or one of the well-known bloat-estimation queries/tools (`pgstattuple`, `pg_bloat_check`, `pg_repack`'s diagnostics).
- **Table/index size vs expected**: compare `pg_total_relation_size` growth to actual row-count growth; disproportionate growth signals bloat.
- **Query performance**: growing seq scan times or bigger-than-expected index sizes for a table with a fairly stable row count.
- **XID age**: `age(relfrozenxid)` in `pg_class` — approaching `autovacuum_freeze_max_age` means a forced aggressive (and possibly disruptive) autovacuum is imminent; better to run a manual one proactively.
- **Autovacuum logs**: check `pg_stat_activity`/logs for autovacuum runs being cancelled (e.g., by conflicting locks) or running unusually long, which means the table isn't getting cleaned reliably.

If dead tuples are high and autovacuum keeps losing the race, a manual `VACUUM (VERBOSE, ANALYZE)` — or `VACUUM FULL`/`pg_repack` if you actually need to reclaim disk space back to the OS — is warranted, along with tuning `autovacuum_vacuum_scale_factor`/`cost_limit` for that table.
