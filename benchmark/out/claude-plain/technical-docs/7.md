## OAuth 2.0 Authorization Code Flow

**Actors:** the user (resource owner), the client application, the authorization server, and the resource server (API).

**Steps:**

1. **Authorization request** – The client redirects the user's browser to the authorization server's `/authorize` endpoint, including its `client_id`, requested `scope`, a `redirect_uri`, a `state` value (CSRF protection), and (with PKCE) a `code_challenge`.
2. **User authentication & consent** – The user logs in at the authorization server (not the client) and approves the requested scopes.
3. **Authorization code returned** – The authorization server redirects back to the client's `redirect_uri` with a short-lived, single-use **authorization code** in the query string, plus the original `state` for verification.
4. **Code exchange** – The client's backend sends the code to the authorization server's `/token` endpoint, along with its `client_secret` (or PKCE `code_verifier` for public clients), to exchange it for an **access token** (and optionally a refresh token).
5. **Resource access** – The client uses the access token to call the resource server's API, typically as a `Bearer` token in the `Authorization` header.

### Why exchange the code for a token server-side rather than returning the token directly

This distinction is what separates the authorization code flow from the older, now-deprecated implicit flow.

- **Browser exposure risk:** The redirect step happens in the user's browser via URL, which is logged in browser history, server access logs, referrer headers, and potentially proxies. A long-lived access token in that URL would be exposed to all of these; a short-lived, single-use code limits the damage if intercepted.
- **Client authentication:** The token exchange requires the `client_secret` (confidential clients) or a PKCE `code_verifier` (public clients like SPAs/mobile apps). This proves the entity redeeming the code is the same one that initiated the request, preventing a stolen code from being used by an attacker who intercepted the redirect but doesn't have the secret/verifier.
- **No token in front-channel:** Access tokens (and refresh tokens) never transit the browser/URL at all — they're returned only in a direct, TLS-protected back-channel HTTP response from the token endpoint to the client's server. This avoids leakage through browser extensions, history, or open redirects.
- **Revocability and shorter blast radius:** The code is single-use and expires in seconds to minutes, so even if leaked, it's nearly useless without the corresponding client credentials, and it can't be replayed after redemption.
- **Refresh tokens:** Only the code flow's back-channel exchange safely supports issuing refresh tokens, since those are even more sensitive than access tokens and must never appear in a browser redirect.

In short, splitting the flow into "get a code" (front-channel, low-value if stolen) and "trade code for token" (back-channel, authenticated) keeps the actual credential off the browser entirely and ties its issuance to proof of client identity.
