Round-robin, least-connections, and consistent hashing solve different problems, so "wrong choice" usually means the choice ignores state, cost, or affinity requirements.

**Round-robin** cycles through backends in fixed order (optionally weighted). It's simple and requires no shared state, which makes it cheap and fast. It assumes all requests cost roughly the same and all backends have equal capacity. It's the wrong choice when request costs vary widely (some requests are 10ms, others are 10s) — a backend can get unlucky and pile up slow requests while others sit idle, since round-robin doesn't look at actual load. It's also wrong when backends have heterogeneous capacity (mismatched sizes) unless you weight it, and wrong when clients need session affinity — round-robin sends each request wherever it's next in line, not to the server holding a client's session state.

**Least-connections** routes each request to the backend with the fewest active connections, which adapts to real-time load and handles uneven request costs far better than round-robin. It's the wrong choice when connection count doesn't correlate with actual load — e.g., long-lived idle connections (WebSockets, keep-alive) can make a backend look "busy" when it's actually free, causing the balancer to avoid it unnecessarily. It also requires the load balancer to track connection state per backend, adding coordination overhead, and in a fleet of balancers (not just one), each with a partial view, the signal can be stale or inconsistent. Like round-robin, it has no built-in affinity, so it's wrong for use cases needing sticky sessions or cache locality.

**Consistent hashing** maps requests to backends based on a hash of some key (user ID, cache key, session ID), so the same key routes to the same backend, and adding/removing a node only remaps a small fraction of keys. This is essential for caching layers, sharded stateful services, or sticky sessions, where locality matters more than perfectly even load. It's the wrong choice when you actually want even load distribution and don't need affinity — hashing can produce hotspots if key popularity is skewed (a viral user ID or cache key overwhelms one node) since it doesn't rebalance based on real load, only based on the key space. It's also a poor fit when backend capacity is uneven or highly dynamic (frequent scale up/down), because although rebalancing is minimized, it's not zero, and virtual-node tuning adds operational complexity for marginal gain if you didn't need affinity in the first place. Finally, it's overkill for stateless services with uniform request cost — you're paying hashing/ring-maintenance complexity for a benefit (affinity) you don't need.

In short: round-robin for uniform, stateless, cheap requests; least-connections for variable-cost stateless requests; consistent hashing for anything requiring affinity or cache locality, accepting some load skew as the tradeoff.
