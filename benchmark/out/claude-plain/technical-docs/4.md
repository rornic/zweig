## How B-tree indexes work

A B-tree (technically B+tree in most databases) is a balanced, sorted tree structure. Each node holds multiple sorted key values with pointers to child nodes; leaf nodes hold the indexed values plus a pointer (or row ID) to the actual table row, and leaves are linked together for fast range scans.

Because the tree is balanced and each node holds many keys (a high "fan-out"), the depth stays small even for huge tables — typically 3-4 levels for millions of rows. Looking up a value means walking from the root down to a leaf, comparing keys at each level, which costs O(log n) disk/page reads instead of scanning every row.

This makes B-trees excellent for:
- **Equality lookups** (`WHERE id = 5`)
- **Range queries** (`WHERE age BETWEEN 20 AND 30`, `ORDER BY created_at`), thanks to the linked leaf nodes
- **Prefix matching** on composite indexes (`WHERE last_name = 'Smith' AND first_name = 'Jane'` if indexed in that order)

## When an index makes queries slower

1. **Low selectivity / low cardinality columns.** An index on a boolean or a column with only a few distinct values (e.g., `status` with 3 possible values) often doesn't narrow the result set enough. The planner may still choose a full table scan — but if it *does* use the index, jumping between the index and the table (random I/O) can be slower than sequentially scanning the whole table.

2. **Queries that return a large fraction of the table.** If a query matches, say, 40% of rows, using an index means many random-access lookups back to the table (unless it's a covering index), which is often costlier than one sequential scan.

3. **Small tables.** If the whole table fits in a few pages, a full scan is already fast; the index adds overhead without benefit.

4. **Write-heavy workloads.** Every `INSERT`/`UPDATE`/`DELETE` must also update every index on the table — rebalancing nodes, splitting pages, etc. Extra indexes slow down writes and increase lock contention, even if they never help a read.

5. **Wrong leading column in a composite index / mismatched sort order.** An index on `(a, b)` doesn't help a query filtering only on `b`. Using it anyway (or the optimizer trying to) wastes effort compared to just scanning.

6. **Non-covering indexes causing "bookmark lookups."** If a query needs columns not in the index, the engine must fetch each matching row from the base table individually, which for many matches is slower than scanning the table once.

7. **Stale statistics.** The query planner picks a scan vs. index-seek based on estimated selectivity. If statistics are outdated, it may choose an index seek for a query that actually matches most of the table, causing far more I/O than a sequential scan would.

**Rule of thumb:** indexes trade write cost and storage for faster *selective* reads. They help when a query narrows to a small percentage of rows; they can hurt when queries are unselective, tables are small, or write throughput matters more than occasional reads.
