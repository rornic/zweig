## Fix stale user profile data served after updates

### Problem
After a user updated their profile, the API could continue serving the old profile data for up to 10 minutes. This was caused by the cache invalidation logic only clearing the primary cache key (`user:{id}:profile`) on write, while read paths also consulted a secondary read-through cache (`user:{id}:profile:v2`) populated by a background refresh job. That secondary key had its own 10-minute TTL and was never invalidated on update, so any request routed through it would return pre-update data until the TTL expired naturally.

### Root cause
The write path (`ProfileService.updateProfile`) called `cache.delete(primaryKey)` but had no knowledge of the derived/versioned cache key used by the read-through layer. The two caching mechanisms were added at different times by different code paths and were never reconciled.

### Fix
- `ProfileService.updateProfile` now invalidates both the primary and versioned cache keys via a shared `invalidateProfileCache(userId)` helper, so there's a single source of truth for "what needs to be cleared on write."
- The read-through cache populator now checks a `lastModified` timestamp against the source-of-truth record before serving a cached entry, as a second line of defense against future cache layers being added without invalidation wired in.
- Added a regression test that updates a profile, then asserts an immediate subsequent read (via both cache paths) returns fresh data rather than the stale cached copy.

### Testing
- New unit test: `ProfileService.test.ts` — update-then-read returns fresh data across both cache keys.
- Manually verified in staging: updated a profile and confirmed reads immediately reflected the change, with no staleness window.

### Risk / rollout
Low risk — invalidation is additive (clears more, not less). No schema or API changes. Safe to deploy without migration.
