## Fix N+1 query in `GET /api/orders` endpoint

### Problem

The orders list endpoint was issuing one query per order to fetch each order's associated `customer` and `line_items`, in addition to the initial query for the order list itself. Locally and in staging this was invisible — small dataset, low latency — but in production, where accounts routinely have hundreds of orders per page, the endpoint was issuing 200+ queries per request. Under concurrent load this saturated the DB connection pool and caused p99 latency on this endpoint to spike to 4-6s, occasionally exhausting the pool and causing timeouts on unrelated endpoints sharing the same pool.

This was found via slow query logs / APM traces in production (not caught by tests or local profiling, since the query count scales with row count and dev fixtures are small).

### Root cause

`OrderSerializer` accessed `order.customer` and `order.line_items` per-instance, and the view's queryset didn't eager-load those relations, so each access triggered a separate lazy-loaded query.

### Fix

- Added `.select_related("customer")` and `.prefetch_related("line_items")` to the queryset in `OrderListView`.
- Reduces the endpoint from `2N + 1` queries to a constant `3` queries regardless of page size.

### Testing

- Added a test asserting query count stays constant as the number of returned orders increases (`assertNumQueries`).
- Verified against a production-sized dataset snapshot (10k orders) locally: response time dropped from ~3.8s to ~180ms for a 200-item page.
- Confirmed no change in response payload/shape.

### Notes

Worth auditing sibling endpoints (`/api/invoices`, `/api/shipments`) for the same pattern — flagged as a follow-up rather than bundling here to keep this fix reviewable.
