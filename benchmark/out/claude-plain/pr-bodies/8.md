## Add idempotency keys to payment processing endpoint

### Problem

The payment endpoint currently has no protection against duplicate submissions. When a client retries a request after a timeout, dropped connection, or ambiguous response (e.g., the charge succeeded but the response never reached the client), we have no way to distinguish a retry from a new payment intent. This can result in customers being charged multiple times for a single purchase.

### Solution

This PR adds support for client-supplied idempotency keys on the payment processing endpoint.

- Clients must pass an `Idempotency-Key` header (UUID) with each payment request.
- On receipt, we check for an existing record matching the key:
  - If none exists, we process the payment normally and store the key alongside the response and a hash of the request payload.
  - If a matching key exists and the request payload hash matches, we return the stored response without reprocessing the charge.
  - If a matching key exists but the payload differs, we reject the request (422) to avoid silently applying a different operation under a reused key.
- Keys are scoped per merchant/account to avoid cross-tenant collisions.
- Stored keys expire after 24 hours, after which the same key can be reused (matches our retry window and keeps storage bounded).
- In-flight requests with the same key (concurrent retries) are handled by locking on the key, so a second request waits for the first to complete rather than racing it.

### Storage

Idempotency records are stored in a new `idempotency_keys` table (key, account_id, request_hash, response body/status, created_at), with a TTL index for expiry.

### Testing

- Unit tests for new-key, matching-retry, conflicting-payload, and expired-key paths.
- Concurrency test simulating two simultaneous requests with the same key to confirm only one charge is created.
- Existing payment endpoint tests updated to include the new required header.

### Rollout

The header is required going forward; clients not yet updated will need a follow-up SDK/docs change. Open to gating this behind a feature flag if we want a soft rollout — flagging for discussion.
