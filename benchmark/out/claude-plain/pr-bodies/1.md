## Fix flaky integration test caused by async setup race condition

### Problem

The `UserSession` integration suite has been intermittently failing in CI (roughly 1 in 15–20 runs), typically with assertion errors claiming session data was missing or stale. The failures were not reproducible locally on demand, which pointed to a timing-dependent bug rather than a logic error.

### Root cause

The test's `beforeEach` hook kicked off two independent async setup calls without establishing an ordering dependency between them:

1. `initializeAuthContext()` — seeds the auth token and user claims
2. `provisionTestWorkspace()` — creates a workspace record and links it to the current user

Both were fired via `Promise.all`, but `provisionTestWorkspace()` internally reads the auth token from a shared context object that `initializeAuthContext()` populates as a side effect partway through its execution, rather than as part of its resolved value. When `provisionTestWorkspace()` happened to reach that read before `initializeAuthContext()` finished writing it, the workspace was created with a null/stale token, and downstream assertions failed non-deterministically depending on scheduler timing.

### Fix

- Made `initializeAuthContext()` return the auth token explicitly instead of relying on a shared mutable context.
- Changed setup to run sequentially: `provisionTestWorkspace()` now takes the token as an explicit parameter and only starts after `initializeAuthContext()` resolves, removing the implicit ordering dependency.
- Removed the now-unused shared context object to prevent the same hazard from recurring elsewhere.

### Testing

- Ran the previously flaky suite 200x locally in a loop with no failures (was failing ~1/15 before the fix).
- Full integration suite passes.
- No changes to production code — this is test-only.
