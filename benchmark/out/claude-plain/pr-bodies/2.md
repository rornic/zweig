## Add `status` column to `orders` table (NOT NULL, backfilled)

### Summary
Adds a `status` column to the `orders` table (~50M rows) to support the new order-lifecycle tracking feature. Since the table is large, this migration is split into safe, non-blocking steps rather than a single blocking `ALTER TABLE ... ADD COLUMN ... NOT NULL`.

### Migration steps
1. **Add column as nullable** with a default value (`status DEFAULT 'pending'`). This is a metadata-only change on Postgres/MySQL 8+ and does not rewrite the table or take a long lock.
2. **Backfill existing rows** in batches (5,000 rows/batch, throttled) via a background script, using the primary key to paginate and avoid full-table scans or long-held locks. Batching also keeps replication lag and WAL/binlog growth manageable.
3. **Add `NOT NULL` constraint** as a separate step once backfill is confirmed complete. On Postgres this uses `NOT VALID` + `VALIDATE CONSTRAINT` to avoid a full-table lock; on MySQL this is a fast operation since the column has no nulls left.
4. **Verify** row count with `status IS NULL` is zero before validating the constraint.

### Why split this way
A single blocking migration on a 50M-row table would hold an exclusive lock for the duration of the backfill, causing write timeouts/downtime. Splitting into nullable-add → backfill → constrain keeps every individual step fast and lock-light.

### Rollout plan
- Deploy schema migration (step 1) first, independent of application code.
- Run backfill script during low-traffic window; monitor replica lag and query latency.
- Deploy step 3 (NOT NULL) only after backfill completes and is verified.
- Application code that depends on `status` being non-null ships after step 3.

### Rollback
- Steps 1–2 are safely reversible (drop column / re-run backfill).
- Step 3 can be reverted by dropping the constraint; no data loss.

### Testing
- Ran migration against a staging snapshot sized ~50M rows; measured backfill duration (~40 min) and confirmed no replication lag spikes or write timeouts.
- Verified idempotency of the backfill script (safe to re-run/resume).
