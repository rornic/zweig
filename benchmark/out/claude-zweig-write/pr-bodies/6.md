## Summary

Replace REST polling with a WebSocket push for the live status dashboard, cutting backend load.

The dashboard currently polls `GET /api/status` every 2s per connected client. At current concurrency this generates sustained request volume with no signal in most responses, since status changes far less often than the poll interval. A WebSocket connection lets the backend push updates only when status actually changes, dropping request volume to near zero at idle and removing the fixed polling floor as client count grows.

## Changes

- Add a WebSocket endpoint (`/ws/status`) that pushes status updates on change, replacing the polling loop in the dashboard client.
- Backend emits a push event from the same code path that currently updates the status store, so there's a single source of truth for "status changed."
- Client falls back to REST polling if the WebSocket connection fails or drops, to avoid a hard dependency on WS availability.
- Remove the polling interval and associated request logic from the dashboard once the WS path is confirmed stable.

## Test plan

- [ ] Confirm dashboard receives pushed updates within one status change cycle, without polling.
- [ ] Kill the WS connection mid-session and confirm the client falls back to polling, then reconnects.
- [ ] Load test with N concurrent dashboard clients, compare backend request volume before/after.
- [ ] Verify no missed updates during a rapid sequence of status changes (no coalescing bugs).
