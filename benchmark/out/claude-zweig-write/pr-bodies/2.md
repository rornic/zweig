## Summary

Adds a `NOT NULL` column to the `orders` table (50M rows) with a backfill, split into three deploy-safe steps instead of one blocking migration.

1. Add the column as nullable with a default value.
2. Backfill existing rows in batches (10k rows per transaction) to avoid long locks and replication lag.
3. Add the `NOT NULL` constraint once the backfill confirms zero remaining nulls.

## Why split it

A single `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT ...` on a 50M-row table takes a full table rewrite and holds a lock for the duration, long enough to cause timeouts on this table's write-heavy path. Splitting into add-nullable, backfill, then constrain keeps every individual step fast and non-blocking.

## Rollout

- Migration runs during off-peak hours; batched backfill throttled to keep replication lag under 5s.
- Application code deploys after the column exists but before the `NOT NULL` constraint lands, so it can start writing the new field without depending on backfill completion.
- The constraint migration only runs once a verification query confirms no nulls remain.
