## fix: invalidate user profile cache on write instead of relying on ttl expiry

Profile updates were served stale for up to 10 minutes because the cache only expired on TTL, not on write. A user could change their profile, get a stale read from any node whose cache hadn't expired yet, and see the old data reflected back to them or to other viewers until the 10-minute window closed.

### Changes

- Invalidate the profile cache entry synchronously as part of the update transaction, before returning a success response to the caller.
- Key the cache by user ID rather than by user ID + fields-requested, so a partial-field update can't leave other cached shapes of the same profile stale.
- Add a regression test that writes a profile, reads it back immediately, and asserts the fresh value is returned (previously this would flake against the stale cache).

The fix invalidates rather than updates the cache entry in place, so the next read repopulates it from the source of truth. This costs one extra cache miss per update but avoids a second class of bug: a read-modify-write race where two concurrent updates could otherwise leave the cache holding a value that matches neither write.

TTL is left at 10 minutes; it's still the right ceiling for cache staleness under normal read traffic, and lowering it would just trade this bug for higher load on the backing store. The real fix was making writes invalidate the cache, not shortening the window this bug happened to expose.
