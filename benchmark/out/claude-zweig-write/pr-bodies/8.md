## Add idempotency keys to payment processing endpoint

### Summary

- Require an `Idempotency-Key` header on `POST /payments`. Requests without one are rejected with `400`.
- Store the key alongside the resulting charge (or error) for 24 hours. A retried request with the same key returns the original response instead of creating a new charge.
- Concurrent requests with the same key while the first is still in flight get a `409` rather than racing each other to charge twice.
- Keys are scoped per merchant account, so two merchants can reuse the same key value without colliding.

### Why

Clients retry on timeouts and network errors, but a timeout doesn't mean the charge failed, it might have succeeded and the response never made it back. Without idempotency keys, that retry creates a second charge. This has already caused duplicate-charge support tickets; this closes that gap at the API level rather than relying on client-side dedup, which we can't guarantee for third-party integrators.

### Design notes

- Keys are stored in the `idempotency_keys` table, not the payments table, so we can support future endpoints (refunds, payouts) without schema changes.
- 24-hour TTL matches our card network's own retry window; a cleanup job purges expired keys.
- Response caching includes the status code and body, not just success, so retries after a declined charge return the same decline rather than double-attempting it.

### Test plan

- Unit tests for key storage, lookup, and expiry.
- Integration test for concurrent duplicate requests (verifies `409`, not a double charge).
- Manual test against staging with a simulated timeout-then-retry.
