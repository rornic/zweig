A cache cluster splits its key space across N nodes so no single machine holds everything. The naive approach hashes each key and takes `hash(key) mod N` to pick a node. It's simple and spreads keys evenly, but it collapses the moment N changes.

Add or remove a node and N changes, so `mod N` changes for nearly every key. A cluster going from 4 nodes to 5 remaps something like 80% of keys to a different owner. Every one of those keys is now a cache miss: the value sits on the old node, but lookups query the new one and find nothing. At cluster scale, that's a thundering herd against the backing database right when the cluster is already in flux from a scaling or failover event.

Consistent hashing fixes this by hashing nodes and keys onto the same ring (typically 0 to 2^32-1, using something like MD5 or the top 32 bits of SHA-1). Each node's hash places it at a point on the ring. To find a key's owner, hash the key and walk clockwise to the first node encountered. Ownership is a proximity relationship on the ring, not an arithmetic function of the current node count.

That changes what happens when membership changes. Adding a node only remaps the keys between it and its counterclockwise neighbor, the ones that now find a closer node first. Removing a node only remaps that node's own keys, which fall to the next one clockwise. Everyone else's key-to-node mapping is untouched. Expected remap fraction is roughly 1/N (or 2/N for a removal), not a near-total reshuffle.

Plain ring hashing has its own problem: with few nodes, hash points cluster unevenly and some nodes end up owning a disproportionate share of the ring. The standard fix is virtual nodes, hashing each physical node to dozens or hundreds of points on the ring instead of one. More points per node smooths the distribution and means a single node's failure spreads its load across many neighbors instead of dumping it all on one.

This is why systems like Memcached client libraries, DynamoDB, Cassandra, and Riak use consistent hashing for partitioning. Rendezvous hashing (highest random weight) solves the same problem with a different mechanism, computing a weight per node per key and picking the max, and is a viable alternative where its O(N) lookup cost per key is acceptable.

The tradeoff against modulo hashing is small bookkeeping (maintaining the ring, tracking virtual nodes) for a large operational win: nodes can join and leave a live cluster with proportional, not catastrophic, cache disruption.
