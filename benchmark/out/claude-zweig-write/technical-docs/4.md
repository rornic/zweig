A B-tree index stores a copy of the indexed column(s), sorted, in a balanced tree structure, with each row's value paired to a pointer at the row's location on disk. Internal nodes hold routing keys that narrow the search range, and leaf nodes hold the actual values plus pointers, usually linked to their neighbors so range scans can walk sideways without returning to the root. A lookup descends from the root, comparing the search key at each node and following the matching branch, reaching any leaf in O(log n) comparisons regardless of table size. This is why indexes speed up equality lookups, range scans, and sorted or grouped reads: the tree prunes most of the table before touching it.

The index isn't free. Every insert, update, or delete on an indexed column has to update the index too, splitting or merging nodes to keep the tree balanced. A table with five indexes pays that cost five times per write, which is why write-heavy tables with many indexes see slower inserts and updates.

Indexes can also make reads slower, in a few distinct ways:

**Low selectivity.** An index on a boolean or low-cardinality column (like `is_active`) often returns such a large fraction of the table that the optimizer would do more I/O following pointers to scattered rows than just scanning the table sequentially. A good optimizer detects this and ignores the index, but a bad cardinality estimate can make it choose the index anyway, producing a plan worse than a full scan.

**Random I/O from bookmark lookups.** Unless an index is covering (it contains every column the query needs), each matched row requires a separate trip to the table's data pages to fetch the rest of the row. On a spinning disk, or even on SSD at scale, thousands of scattered lookups following a range scan can cost more than one sequential pass over the table.

**Write amplification cascading into reads.** Heavily indexed tables under high write load spend more time on index maintenance, which can starve concurrent read queries of I/O bandwidth and lock resources, even if each individual index seek is fast.

**Planner misdirection.** Extra indexes give the query optimizer more candidate plans to evaluate and more chances to pick wrong, especially with stale statistics. A new index can shift the optimizer away from a previously-good plan and toward a worse one, for queries that don't even reference the new index directly.

The rule of thumb: index columns used in `WHERE`, `JOIN`, or `ORDER BY` clauses with high selectivity, and verify with `EXPLAIN` rather than assuming more indexes help.
