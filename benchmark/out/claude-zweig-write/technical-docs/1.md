When you type a URL and hit enter, the browser first checks its own DNS cache, then the OS cache, for a recent answer to "what's the IP for this hostname." If neither has one, the OS hands the query to a resolver, usually one run by your ISP or a public one like 8.8.8.8 or 1.1.1.1.

That resolver does the real work. It doesn't know the answer either, so it starts at the top of the DNS hierarchy and works down.

First it asks a root server, one of thirteen well-known addresses baked into every resolver. The root server doesn't know the IP for your domain, but it knows which server handles the top-level domain, `.com`, `.org`, whatever follows the last dot. It points the resolver there.

Next the resolver asks that TLD server. The TLD server doesn't know the final IP either, but it knows which nameserver is authoritative for your specific domain, the one the domain's owner configured when they set up DNS (often through their registrar or a provider like Cloudflare or Route 53). It points the resolver there.

Finally the resolver asks the authoritative nameserver, and this one actually has the answer: an A record (IPv4) or AAAA record (IPv6) mapping the hostname to an IP address. It returns that IP to the resolver, which returns it to your OS, which hands it to the browser.

Three hops to find the answer (root, TLD, authoritative), then one more back to you. That's a full recursive lookup, and it only happens on a cache miss. Every DNS record has a TTL, a number of seconds it's allowed to sit in cache before it's considered stale. Short TTLs (like 60 seconds) mean you can update a record and have it propagate fast, at the cost of more lookups. Long TTLs (hours or days) mean fewer lookups but slower propagation if you change something. This is why after you update a DNS record, some people still hit the old IP for a while, their resolver is serving a cached answer that hasn't expired yet.

Once the browser has the IP, DNS's job is done. It opens a TCP connection to that address, negotiates TLS if it's HTTPS, and sends the actual HTTP request. DNS just answered "where do I send this," it says nothing about what happens once you get there.

One practical note for debugging: `dig` or `nslookup` let you run this lookup manually and see exactly which server answered and with what TTL, which is usually the fastest way to tell whether a "site is down" problem is actually a DNS problem.
