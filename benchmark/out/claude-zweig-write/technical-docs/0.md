# Runbook: Pod Stuck in CrashLoopBackOff

## 1. Confirm the state

```
kubectl get pod <pod> -n <namespace>
```

Check `RESTARTS` and `AGE`. A high restart count with short age confirms a crash loop, not a slow start.

## 2. Read the exit code and last state

```
kubectl describe pod <pod> -n <namespace>
```

Look at `Last State > Terminated`:

- **Exit Code 0**: the container's main process exited cleanly. The image's entrypoint likely isn't a long-running process, or a script finishes and returns.
- **Exit Code 1**: generic application error. Check logs.
- **Exit Code 137**: SIGKILL, usually an OOM kill. Confirm with `Reason: OOMKilled` in the same output. Fix by raising `resources.limits.memory` or fixing a leak.
- **Exit Code 143**: SIGTERM, often the app not handling graceful shutdown before Kubernetes escalates to SIGKILL.
- **Exit Code 139**: segfault, points at the binary or a native dependency.

Also check `Events` at the bottom of `describe` output for `Liveness probe failed`, `Readiness probe failed`, `FailedMount`, or `Back-off restarting failed container`.

## 3. Check logs

```
kubectl logs <pod> -n <namespace> --previous
```

`--previous` is essential: the current container instance may not have logged anything yet, but the one that just crashed did. If logs are empty even with `--previous`, the crash happens before the app writes anything, i.e. missing config, a bad entrypoint, or a missing binary in the image.

## 4. Check config and secrets

```
kubectl get pod <pod> -n <namespace> -o yaml
```

Verify every `envFrom` / `env.valueFrom` reference resolves, that mounted `ConfigMap`s and `Secret`s exist in the same namespace, and that file paths in `volumeMounts` match what the app expects. A missing referenced Secret shows as `CreateContainerConfigError` in pod status rather than a crash loop, so rule that out first.

## 5. Check liveness/readiness probes

A misconfigured liveness probe (too short `initialDelaySeconds`, wrong path or port) kills a healthy container before it finishes starting up. Compare the probe's `periodSeconds` / `failureThreshold` against the app's actual startup time. Temporarily removing the probe (in a test environment) isolates whether the probe or the app itself is the cause.

## 6. Reproduce locally

```
docker run --rm -it <image> <command from the pod spec>
```

Runs the exact image and entrypoint outside Kubernetes. This isolates image and application bugs from cluster-specific issues like config, secrets, or probes.

## 7. Check resource limits

```
kubectl top pod <pod> -n <namespace>
```

If usage sits near or over `resources.limits.memory`, treat it as OOM even without an explicit `137` (the kubelet can evict before the container fully reports its exit code).

## Common root causes, ranked by frequency

1. Application error from bad config or a missing environment variable.
2. OOMKilled from limits set too low.
3. Liveness probe misconfigured, killing a still-starting app.
3. Missing dependency (database, downstream service) the app requires at startup and doesn't retry.
5. Wrong command or entrypoint in the pod spec, exiting immediately.

## Resolution checklist

- Fix the root cause identified above (code, config, resource limits, or probe settings).
- Redeploy: `kubectl rollout restart deployment/<name> -n <namespace>`.
- Watch recovery: `kubectl get pod <pod> -n <namespace> -w`.
- If restarts continue, delete the pod to force a clean respawn and re-check logs from the new instance: `kubectl delete pod <pod> -n <namespace>`.
