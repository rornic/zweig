# Rebase vs. Merge

## Rebase before opening a PR

Run `git rebase main` on your feature branch first. This keeps history linear and makes each commit reviewable on its own. Force-push after (`git push --force-with-lease`), since rebase rewrites commit hashes.

- Only rebase branches nobody else has pulled. Once someone else has commits on top of yours, rebasing rewrites shared history and breaks their branch.
- Never rebase `main`. It's shared, and rewriting it forces everyone else to reconcile diverged histories.
- Resolve conflicts commit by commit. Rebase replays your commits one at a time onto the new base, so you may hit the same conflict more than once if it spans several commits.

## Merge into main

A PR merges into `main` as a real merge commit, not a rebase or squash, unless the team has agreed on squash for that repo. The merge commit marks where a feature landed and groups its commits for `git bisect` and `git log --first-parent`.

## When to use each

**Rebase:**
- Updating your feature branch with the latest `main` before or during review, as long as no one else has pulled your commits yet.
- Cleaning up your own commit history before opening a PR (squashing WIP commits, reordering, rewriting messages) via `git rebase -i`.
- Any branch that's still private to you.

**Merge:**
- Landing a finished PR into `main`.
- Combining a branch other people have already pulled or built on (rebasing it would rewrite commits they depend on).
- You want an explicit record of when and how branches diverged and joined.

## Why the confusion

Both commands answer "how do I combine this branch with that one," but they preserve different things. Merge preserves the actual sequence of events. Two branches existed, then joined. Rebase preserves a clean story, as if you'd built your feature on `main` all along, discarding the messier true order.

Pick based on whether the branch is still private (rebase freely) or already shared (merge, don't rebase). That's the one rule that resolves most of the disagreements.

## If you rebase and break something

If you force-push a rebased branch and a teammate's local copy diverges, they need to reset their branch to match yours (`git fetch && git reset --hard origin/<branch>`), not merge the two histories. Warn them before you force-push a shared branch, or better, don't rebase it at all.
