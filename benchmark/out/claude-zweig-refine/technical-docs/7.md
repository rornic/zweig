The authorization code flow lets a client application (a web app, typically) obtain an access token to call an API on a user's behalf, without ever handling the user's credentials.

**The steps**

1. The client redirects the user's browser to the authorization server's `/authorize` endpoint, with a `client_id`, `redirect_uri`, requested `scope`, and a `state` value (a random string the client will check later to prevent CSRF).
2. The user authenticates at the authorization server and approves the requested scopes.
3. The authorization server redirects back to the client's `redirect_uri` with a short-lived, single-use authorization code and the original `state`.
4. The client's backend sends that code, its `client_id`, and its `client_secret` directly to the authorization server's `/token` endpoint, a server-to-server call rather than a browser redirect.
5. The authorization server validates the code and credentials, then returns an access token (and usually a refresh token) in the response body.

**Why the code, not the token, comes back through the browser**

The redirect in step 3 travels through the user's browser, landing in the URL bar, browser history, referrer headers, and server logs along the way, exposed to browser extensions and network intermediaries as well as the user.

An authorization code is deliberately cheap to leak. It's single-use, expires in seconds to minutes, and is worthless without the client secret, which lives only on the backend.

None of that applies to an access token, the actual credential for calling the API, often valid for an hour or more. Returned directly through the browser redirect, as the older implicit flow did, it would sit in browser history, replayable by anyone who intercepted it with no further check required.

Splitting the exchange this way, public code over the browser, secret-gated swap on the backend, also lets the authorization server verify the client's identity (via `client_secret`, or a PKCE (Proof Key for Code Exchange) `code_verifier` for public clients that can't hold a secret) before issuing the real credential. That verification step is exactly what's missing when the token comes back directly, which is why the implicit flow is now deprecated in favor of authorization code plus PKCE, even for browser-based and mobile clients.
