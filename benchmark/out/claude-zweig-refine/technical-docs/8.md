Postgres uses MVCC, so every UPDATE writes a new row version instead of overwriting the old one, and DELETE marks a row dead rather than removing it. Old versions stick around because some transaction might still need them under snapshot isolation. Autovacuum is the background process that reclaims dead rows. It scans tables, marks the space they occupied as free for reuse by future inserts and updates, and updates planner statistics so query plans stay accurate. It also freezes old transaction IDs to prevent transaction ID wraparound, a rarer but more dangerous failure mode than bloat.

Table bloat happens when dead rows accumulate faster than autovacuum reclaims them, either because it isn't running or it's tuned too conservatively for the write rate. The table file grows even though the live row count stays flat. Postgres doesn't shrink files on disk automatically; it only marks space free for reuse. A long-running transaction makes this worse. MVCC can't remove any row version newer than the oldest snapshot still active, so an idle transaction left open for hours (a common culprit is an ORM connection pool holding a transaction, or a forgotten `BEGIN` in a psql session) blocks cleanup across every table it touches, not just the ones it queries. High-churn tables (queues, session stores, counters updated on every request) bloat fastest because they generate the highest ratio of dead-to-live tuples.

Bloat costs you three ways: queries do more I/O scanning dead tuples, indexes bloat alongside the table and slow down lookups, and on-disk size can balloon well past what the live data needs.

To check if a table needs a manual VACUUM, query `pg_stat_user_tables`:

```sql
SELECT relname, n_dead_tup, n_live_tup, last_autovacuum, last_vacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

A high `n_dead_tup` relative to `n_live_tup` (roughly 20% or more is worth investigating) means dead rows are outpacing cleanup. A `last_autovacuum` that's null or far in the past on a high-churn table suggests autovacuum isn't keeping up, often because the default thresholds (`autovacuum_vacuum_scale_factor` at 20% of table size) are too coarse for a large table. Check `pg_stat_activity` too, for long-running or idle-in-transaction sessions holding back the cleanup horizon.

An unchanged table size after a plain `VACUUM` doesn't mean it failed. VACUUM frees space for reuse, not disk, so the file doesn't shrink. Only `VACUUM FULL` or `pg_repack` reclaim disk space, at the cost of an exclusive lock (`VACUUM FULL`) or extra disk and CPU during a rebuild (`pg_repack`). For ongoing bloat rather than a one-off, tune autovacuum's scale factor down per table instead of relying on manual runs.
