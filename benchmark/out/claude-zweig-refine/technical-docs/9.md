**Round-robin** cycles requests through backends in fixed order, blind to what each one is currently doing. It's cheap and trivially fair when every backend has the same capacity and every request costs roughly the same. It's the wrong choice the moment either assumption breaks. Mix in a slow node (different hardware, a JVM still warming up, a noisy neighbor) or requests of wildly different cost (one triggers a report generation, the next a cache hit), and round-robin keeps feeding the struggling backend its equal share anyway. Queues build unevenly, latency percentiles blow out, and nothing in the algorithm notices.

**Least-connections** routes each request to whichever backend currently holds the fewest open connections, fixing the problem round-robin ignores. Struggling nodes accumulate connections and get skipped. It breaks down wherever connection count stops being a proxy for load. Long-lived idle connections (keep-alives, WebSockets, pooled DB clients) inflate a backend's count without adding work, so it gets starved of new traffic it could easily handle. Very short-lived requests move too fast for the counter to mean anything between decisions, collapsing the algorithm back to something like random choice. Heterogeneous request costs defeat it the same way they defeat round-robin. Five cheap connections and five expensive ones look identical to a counter that only tracks quantity.

The same key should always land on the same node. That's what **consistent hashing** buys you, by mapping each request to a backend via a hash of some key (client IP, session ID, cache key). Adding or removing a node then only remaps a small fraction of keys instead of reshuffling everything, and that property is the entire point. It's for when you need affinity (session stickiness, cache locality, sharding) and want scaling events to be cheap. It's the wrong tool the instant load, not affinity, is the goal. If keys aren't uniformly popular (one tenant, one cache key, one session dominates traffic), that hot key pins disproportionate load onto a single node with no mechanism to redistribute it, since the whole design resists rebalancing. And if the service is stateless and doesn't need repeat requests to hit the same backend, consistent hashing adds a ring, virtual nodes, and rehashing logic to solve a problem you don't have, while giving up the even spread that round-robin or least-connections would provide for free.

Round-robin assumes uniform backends and uniform requests. Least-connections assumes connection count tracks actual load. Consistent hashing assumes you need affinity and can tolerate uneven distribution to get it. Pick one without checking its assumption against your actual traffic shape, and you get a load balancer that's technically working and a fleet that isn't balanced at all.
