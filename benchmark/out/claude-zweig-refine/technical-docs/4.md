A B-tree index stores a sorted copy of the indexed column(s) in a balanced tree, each value paired with a pointer to the row's location on disk. Internal nodes hold routing keys that narrow the search range. Leaf nodes hold the values and pointers, usually linked to their neighbors so a range scan can walk sideways without returning to the root. A lookup descends from the root, comparing the search key at each node and following the matching branch, reaching any leaf in O(log n) comparisons regardless of table size. That's why indexes speed up equality lookups, range scans, and sorted or grouped reads. The tree prunes most of the table before touching it.

The index isn't free. Every insert, update, or delete on an indexed column has to update the index too, splitting or merging nodes to keep the tree balanced. A table with five indexes pays that cost five times per write, so write-heavy tables slow down as indexes accumulate.

Indexes can also make reads slower in a few distinct ways.

**Low selectivity.** An index on a boolean or low-cardinality column (like `is_active`) often returns such a large fraction of the table that following pointers to scattered rows costs more I/O than a sequential scan. A good optimizer detects this and ignores the index, but a bad cardinality estimate can make it choose the index anyway, producing a plan worse than a full scan.

**Random I/O from bookmark lookups.** Unless an index is covering (it contains every column the query needs), each matched row requires a separate trip to the data pages to fetch the rest of the row. On a spinning disk, or even on SSD at scale, thousands of scattered lookups after a range scan can cost more than one sequential pass over the table.

**Write amplification cascading into reads.** Heavily indexed tables under high write load spend more time on index maintenance, which can starve concurrent reads of I/O bandwidth and lock resources even when each index seek is fast.

**Planner misdirection.** A new index can shift the optimizer away from a previously-good plan and toward a worse one, even for queries that never reference it directly. Extra indexes just mean more candidate plans to weigh, and more chances to pick wrong, especially with stale statistics.

Index columns that are used in `WHERE`, `JOIN`, or `ORDER BY` clauses and have high selectivity, then verify with `EXPLAIN` rather than assuming more indexes help.
