When you type a URL and hit enter, the browser first checks its own DNS cache, then the OS cache, for a recent answer to "what's the IP for this hostname." If neither has one, the OS hands the query to a resolver, usually one run by your ISP or a public one like 8.8.8.8 or 1.1.1.1.

That resolver does the real work. It doesn't know the answer either, so it starts at the top of the DNS hierarchy and works down.

First it asks a root server, one of thirteen well-known addresses baked into every resolver. The root server doesn't know the IP for your domain, but it knows which server handles the top-level domain (`.com`, `.org`, whatever follows the last dot), and points the resolver there.

Next the resolver asks that TLD server. The TLD server doesn't know the final IP either, but it knows which nameserver is authoritative for your specific domain, the one the domain's owner configured when they set up DNS (often through their registrar or a provider like Cloudflare or Route 53), and points the resolver there.

The authoritative nameserver is where the chain ends. It holds the real answer, an A record (IPv4) or AAAA record (IPv6) mapping the hostname to an IP address, and hands that back to the resolver, which passes it to your OS, which passes it to the browser.

Three hops to find the answer (root, TLD, authoritative), then one more back to you. That's a full recursive lookup, and it only happens on a cache miss, since the resolver caches the answer it gets back for as long as the TTL allows. Every DNS record has a TTL, a number of seconds it's allowed to sit in cache before it's considered stale. Short TTLs, say 60 seconds, mean fast propagation but more lookups. Long TTLs, hours or days, mean fewer lookups but slow propagation. This is why after you update a DNS record, some people still hit the old IP for a while. Their resolver is serving a cached answer that hasn't expired yet.

Once the browser has the IP, DNS's job is done. It opens a TCP connection to that address, negotiates TLS if it's HTTPS, and sends the actual HTTP request. DNS just answered "where do I send this." It says nothing about what happens once you get there.

`dig` or `nslookup` run this lookup manually and show exactly which server answered and with what TTL, usually the fastest way to tell whether a "site is down" problem is actually a DNS problem.
