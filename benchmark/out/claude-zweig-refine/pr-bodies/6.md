## Summary

The dashboard currently polls `GET /api/status` every 2s per connected client. Status changes far less often than that, so most requests return nothing new, and volume scales with client count either way.

This replaces polling with a WebSocket push. The backend sends an update only when status actually changes, so request volume drops to near zero at idle and stops scaling with client count.

## Changes

- Add a WebSocket endpoint (`/ws/status`) that pushes updates on change, replacing the dashboard's polling loop.
- The backend emits the push from the same code path that updates the status store, so there's one source of truth for "status changed."
- WebSocket failures or drops aren't a hard outage. The client falls back to REST polling.
- Once the WS path is confirmed stable, remove the dashboard's default 2s polling loop. The REST fallback used on WebSocket failure stays.

## Test plan

- [ ] Confirm the dashboard receives a pushed update on the first status change, with no polling.
- [ ] Kill the WS connection mid-session and confirm the client falls back to polling, then reconnects.
- [ ] Under N concurrent dashboard clients, backend request volume should drop sharply versus the polling baseline.
- [ ] Verify no missed updates during a rapid sequence of status changes (no coalescing bugs).
