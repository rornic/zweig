## Add idempotency keys to payment processing endpoint

### Summary

- Require an `Idempotency-Key` header on `POST /payments`. Missing the header returns a `400`.
- Store the key alongside the resulting charge (or error) for 24 hours. A retry with the same key then returns that response instead of creating a new charge.
- A concurrent request with the same key, while the first is still in flight, gets a `409` instead of racing to a double charge.
- Keys are scoped per merchant account, so two merchants can safely reuse the same key.

### Why

Clients retry on timeouts and network errors, but a timeout doesn't mean the charge failed. It might have succeeded and the response never made it back. Without idempotency keys, that retry creates a second charge, and it already has, generating the duplicate-charge tickets that prompted this fix. Closing the gap at the API level beats relying on client-side dedup, which we can't guarantee for third-party integrators.

### Design notes

- Keys are stored in the `idempotency_keys` table, not the payments table, so we can support future endpoints (refunds, payouts) without schema changes.
- The 24-hour TTL matches our card network's own retry window. A cleanup job purges expired keys.
- Response caching includes the status code and body, not just success, so retries after a declined charge return the same decline rather than double-attempting it.

### Test plan

- Unit tests for key storage, lookup, and expiry.
- Concurrent duplicate requests get an integration test verifying a `409`, not a double charge.
- Manual test against staging with a simulated timeout-then-retry.
