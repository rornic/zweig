fix: eager-load associations to remove n+1 query on `GET /orders`

- replace the per-order lookup in `OrdersController#index` with a single eager-loaded query (`includes(:line_items, :customer)`), cutting query count from O(n) to a fixed 3 regardless of page size
- add a `bullet` gem check in CI so future n+1s fail the build instead of surfacing only under load
- add a load test fixture (500 orders, 5k line items) to the perf suite to catch regressions

The endpoint was fast in staging and in every manual test. Staging never carries enough orders per page to expose the lookup. Production load pushed p99 latency past 4s during peak traffic, and a Honeycomb trace showed one query per order for `line_items` and another for `customer`, both issued inside a loop in the serializer. Query count scaled linearly with page size, so it stayed invisible until real traffic pushed page size and concurrency high enough to saturate the connection pool.

The fix moves the association loading into the controller query instead of the serializer, so ActiveRecord issues one query per association rather than one per row. Verified against production traffic replay. p99 dropped from 4.1s to 180ms at the same load, and connection pool checkout wait time returned to baseline.
