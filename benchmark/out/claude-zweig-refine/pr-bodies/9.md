## Summary

Migrates background jobs off the monolith's in-process scheduler and onto a queue-based worker pool, decoupling execution from the request/response lifecycle.

Today, scheduled and triggered jobs run inline in the monolith process. A slow or stuck job ties up application resources, a deploy or restart drops any job mid-run with no retry, and job load competes with request traffic for CPU and memory. As job volume grows, this has caused request latency spikes during heavy job windows and silent job loss during deploys.

The monolith now enqueues jobs instead of running them directly. Workers pull, execute, and acknowledge jobs on their own, so a failure retries without an app restart and job load no longer competes with request traffic.

## Changes

- Add a job queue (producer/consumer) and worker process, replacing the in-process scheduler
- Convert existing scheduled jobs to queue producers, each job type with its own queue message schema
- Add retry with exponential backoff and a dead-letter queue for jobs that exhaust retries
- Add worker health checks and horizontal scaling config so worker capacity can flex independently of the monolith
- Remove the in-process scheduler and its cron-style registration code
- Add metrics for queue depth, job latency, and failure rate

## Migration notes

- Jobs are cut over one at a time behind a feature flag, so the old scheduler and new workers can run side by side during rollout and a misbehaving job type can flip back to the old scheduler
- In-flight jobs on the old scheduler are allowed to drain before their flag flips. No job is force-killed mid-run
- Idempotency keys are added to job payloads, since queue delivery is at-least-once and a worker crash after execution but before acknowledgement can redeliver a job
