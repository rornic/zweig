## fix: invalidate user profile cache on write instead of relying on ttl expiry

Profile updates were served stale for up to 10 minutes because the cache expired only on TTL, not on write. A user could update their profile and still see, or show other viewers, the old data from any node whose cache hadn't expired yet.

### Changes

- Invalidate the profile cache entry synchronously inside the update transaction, before it returns success.
- Key the cache by user ID rather than by user ID plus requested fields, so a partial-field update can't leave other cached shapes of the same profile stale.
- Add a regression test that writes a profile, reads it back immediately, and asserts the fresh value comes back (this used to flake against the stale cache).

The fix invalidates rather than updates the cache entry in place, so the next read repopulates it from the source of truth. This costs one extra cache miss per update, but it avoids letting two concurrent writes race to update the same entry, which could otherwise leave the cache holding a value that matches neither write.

TTL stays at 10 minutes. It's still the right ceiling for staleness under normal read traffic, and lowering it would just trade this bug for higher load on the backing store. The real fix was making writes invalidate the cache, not shortening the window this bug happened to expose.
