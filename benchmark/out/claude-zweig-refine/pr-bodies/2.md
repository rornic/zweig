## Summary

Adds a `NOT NULL` column to the `orders` table (50M rows) with a backfill, split into three deploy-safe steps instead of one blocking migration.

1. Add the column as nullable with a default value.
2. Backfill rows where the column is still `NULL`, in batches (10k rows per transaction), to avoid long locks and replication lag. Scoping to `NULL` rows means the backfill can't overwrite values the app has already written.
3. Add the `NOT NULL` constraint once the backfill confirms zero remaining nulls.

## Why split it

A single `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT ...` on a 50M-row table requires a full table rewrite, holding a lock long enough to cause timeouts on this table's write-heavy path. Splitting into add-nullable, backfill, then constrain keeps each step fast and non-blocking.

## Rollout

- Migration runs during off-peak hours. Batched backfill is throttled to keep replication lag under 5s.
- Application code deploys after the column exists but before the `NOT NULL` constraint lands, so it can write the new field without waiting on the backfill.
- The constraint migration runs only after a verification query confirms no nulls remain.
